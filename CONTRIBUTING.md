Правила поведения — [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). О найденной уязвимости пишите приватно, как описано в [SECURITY.md](SECURITY.md), а не в issue. Вопросы и идеи — в Discussions.

## Что нужно

- macOS с Xcode Command Line Tools (`xcode-select --install`), Go 1.27 (версия — в `go.mod`) и сеть: `make` сам скачивает линтер и другие инструменты, кроме `shellcheck` (`brew install shellcheck`); `make test` ещё и собирает архив выпуска.

```sh
git clone https://github.com/Windemiatrix/photosync
cd photosync
make help   # все цели
make test   # все проверки перед PR
```

## Путь изменения

Одинаковый для всех: для мейнтейнера, внешних участников (из ветки форка) и Dependabot. ИИ-агенты, работающие от имени мейнтейнера, идут тем же путём и дополнительно следуют [AGENTS.md](AGENTS.md).

1. Ветка от актуального `main`: `<type>/<тема>`, например `feat/schema-photos12`, `fix/rest-retry`. Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.
2. Сначала тест, потом код (TDD): тест, который падает по нужной причине, затем код, который его проходит. Исправление ошибки начинается с теста, воспроизводящего ошибку.
3. Перед PR локально зелёный `make test` (на macOS): он запускает все проверки, включая линтеры.
4. PR в `main`. В описании — что и зачем меняется. Прямых push в `main` нет.
5. Зелёный `ci-ok`: он сводит все обязательные проверки в одну.
6. Слияние — только squash, его делает мейнтейнер. Одобрений пока не требуется, потому что разработчик один; слияние остаётся решением мейнтейнера.

## Заголовок PR

Заголовок PR становится заголовком коммита в `main`, а из заголовков собирается список изменений в заметках к релизу.

- Формат `<type>(<scope>)[!]: <описание>`, например `feat(schema): add photos12 schema`. Scope обязателен: строчные латинские буквы, цифры, `._/-`.
- Несовместимое изменение (команды, флаги, ключи конфигурации, схема state) помечается `!` сразу после scope: `feat(config)!: rename remotes key`. Это единственный маркер: он определяет следующую версию (раздел «Выпуск») и выносит заголовок в группу «Breaking changes» заметок к релизу. `BREAKING CHANGE:` в теле не распознаётся: тело squash-коммита пустое. Без scope (`feat!: …`) заголовок отклоняется.
- Английский, только печатные ASCII-символы, не длиннее 70 символов, без `#<номер>`: GitHub сам дописывает ` (#<номер PR>)`.
- Проверяет workflow `pr-title` при открытии PR, каждом push и каждой правке заголовка. До открытия PR заголовок можно проверить локально: `make pr-title PR_TITLE='...'`.
- **В окне squash-слияния заголовок и тело коммита не редактируются.** Править можно только заголовок PR: иначе в `main` попадёт заголовок, который проверка не видела.
- Заголовки коммитов внутри ветки не проверяются: squash их отбрасывает.

## Упавший выпуск на `main`

История `main` не переписывается: force-push и удаление запрещены, теги неизменяемы. Упавший job `release` на `main` чинится следующим PR.

## Зависимости

Новая прямая зависимость — отдельный PR с обоснованием: зачем она нужна, почему не хватает стандартной библиотеки, какая у неё лицензия (совместимая с MIT) и как она сопровождается. `go.mod` и `go.sum` проверяет мейнтейнер.

## Язык

- Код, комментарии, сообщения коммитов и заголовки PR — на английском.
- Документы — на русском и английском одновременно, смысл совпадает: `*.md` и `*.en.md`.

## Личные данные

Публичная история необратима: форки и архивы сохраняют всё, что однажды попало в репозиторий. В коммиты и PR не попадают:

- библиотеки «Фото», `*.sqlite*`, `state.db`, `runs/`, `*.jsonl`, отчёты и журналы запусков;
- пароли, токены, `client_secret`, файлы токенов (`~/.config/photosync/tokens/`);
- названия ваших альбомов, пути в облаке, логины, UUID и GUID, точные числа вашей медиатеки.

В тестах и документах — обобщённые примеры: `IMG_0001.HEIC`, `2024/05-01 - Holidays`, `user@example.com`. Фикстуры из реальных материалов допустимы только как результат `tools/anonymize`: сканер утечек проверяет их, автоматическая сверка с исходными материалами (`make fixtures-verify`) подтверждает, что слова входа в них не попали, а мейнтейнер читает сводку этой сверки. Необязательно: перед коммитом прогонять `gitleaks` и личный список запрещённых строк, который хранится вне репозитория.

## Тесты, меняющие «Фото»

Тесты с тегом `photokit_live` импортируют, меняют и удаляют объекты настоящей медиатеки. Их запускают только вручную, под отдельной учётной записью macOS с отдельным Apple ID и тестовой медиатекой, никогда на своей основной медиатеке и не в CI. Остальные тесты медиатеку не трогают.

## Внешние участники

- Для PR из форка CI запускается после одобрения мейнтейнера.
- PR, меняющий `.github/`, `scripts/`, `Makefile`, `.goreleaser.yaml`, `.svu.yml`, `docs/release-notes-header*.md`, `go.mod` или `go.sum`, объясните в описании: мейнтейнер проверяет, что изменение не ослабляет проверки. `.goreleaser.yaml` и шапка заметок исполняются в job выпуска с правом записи.
## Выпуск

Релиз выходит сам после каждого слияния PR в `main`. Когда CI на этом коммите зелёный, job `release` в `ci.yml` вычисляет версию, собирает универсальный бинарник, подписывает его ad-hoc, пакует архив, считает `checksums.txt`, публикует GitHub Release (он же создаёт тег на этом коммите) и подтверждает происхождение. Заметки собираются из заголовков PR, `CHANGELOG.md` не ведётся.

Версию никто не назначает: её вычисляет [svu](https://github.com/caarlos0/svu) по заголовкам PR с последнего тега, правила — в `.svu.yml`. Следующую версию показывает `make next-version`.

| Заголовки с последнего тега | до `1.0.0` | с `1.0.0` |
|---|---|---|
| есть `type(scope)!:` | minor | major |
| иначе есть `feat(…)` | minor | minor |
| иначе любые другие | patch | patch |

Версия `1.0.0` из заголовков не выводится: её выпускает мейнтейнер ручным запуском `ci.yml` (Run workflow) с флагом `major`.

Опубликованный тег не переносится; ошибочную версию закрывает следующая.
