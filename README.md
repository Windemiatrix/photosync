# photosync

[English](README.en.md) | **Русский**

Консольная программа для macOS, которая синхронизирует медиатеку «Фото» (iCloud Photos) с облачным хранилищем; в первой версии это Яндекс Диск через его REST API. Фотографии и видео лежат в облаке обычными папками (`Год/ММ-ДД - Название`), а альбомы «Фото» соответствуют каталогам. Изменения идут в обе стороны: новое с Mac уходит в облако, новое из облака импортируется в «Фото».

## Статус

**Проектирование. Релизов нет, код синхронизации ещё не написан.** Архитектура описана, исследования поведения macOS, PhotoKit и Яндекс Диска завершены; оставшиеся неизвестные (импорт в общую медиатеку, стабильность облачных идентификаторов) зависят от iCloud и проверяются по ходу реализации. Всё ниже описывает задуманное поведение, а не готовую программу.

## Зачем

- Хранить в облаке вторую, понятную человеку копию медиатеки: открывается в любом файловом менеджере без «Фото».
- Не зависеть от одного сервиса: те же файлы доступны с любого устройства и из любой программы.
- Работать с общей и личной медиатеками iCloud. Импорт сразу в общую медиатеку ещё не подтверждён (нужна проверка с iCloud); если он не получится, объект попадёт в личную, а перенос делается вручную по отчёту. Общие альбомы не синхронизируются.
- Заменять ручную синхронизацию: программа сама сопоставляет уже лежащие в облаке файлы с объектами «Фото» и не загружает их повторно.

## Как это будет выглядеть

Планируемый порядок работы (команд ещё нет):

```text
photosync init                  # мастер настройки: хранилища, вход в Яндекс по коду, политики
photosync remote auth <имя>     # вход в Яндекс Диск: код для https://ya.ru/device
photosync remote logout <имя>   # удалить файл токенов и отозвать доступ
photosync doctor                # проверка окружения, прав и доступности хранилищ
photosync plan                  # что будет сделано; ничего не меняет
photosync sync --apply          # выполнить план
```

Команды расписания в первой версии нет: для запуска по расписанию в этом README появится образец plist для LaunchAgent.

Передачи файлов в обе стороны идут параллельно: по умолчанию 256; для медленного канала уменьшите `limits.parallel` в настройках (скан облака им не ограничен).

## Ключевые принципы

- **Сначала план, потом действие.** `photosync plan` ничего не меняет в данных и показывает, что произойдёт. Всё, что меняет данные, выполняется только с `--apply`.
- **Ничего не теряется без явного согласия.** Политика удалений `deletes` обязательна, значения по умолчанию нет: без неё команды, меняющие данные, отказываются работать. Варианты:
  - `none`: удаления не переносятся на другую сторону;
  - `quarantine` (рекомендуется): удалённое с одной стороны уходит в карантин в облаке (`.photosync/quarantine`, 90 дней по умолчанию) или в «Недавно удалённые» в «Фото»; по истечении срока файл в облаке удаляется безвозвратно, минуя корзину;
  - `propagate`: файл в облаке уходит в корзину Яндекс Диска; `undo` его не вернёт, восстановить вручную можно до очистки корзины, а до тех пор он занимает квоту Диска.
- **Опасное подтверждается человеком.** Необратимые операции подтверждаются вводом их числа в терминале, массовые изменения — флагом `--allow-mass-changes` или вводом числа; `--yes` в обоих случаях не действует.
- **Откат.** Каждый запуск пишет журнал; `photosync undo --apply` откатывает только последний применённый запуск, кроме необратимых операций: их список виден заранее.
- **Повторный запуск без изменений ничего не делает**: ноль операций и ноль переданных байт. Исключения: только что появившиеся файлы (они выдерживаются несколько минут), открытые конфликты и запуск с `--limit`.
- **Приватность.** Токены хранятся открытым текстом в файле с правами `0600`: его может прочитать любая программа, запущенная под вашей учётной записью. Сеть — только к API Яндекс Диска, его хостам передачи файлов и OAuth Яндекса: без телеметрии, проверок обновлений и отправки отчётов о сбоях. Локальные отчёты о запусках программа пишет только на ваш диск.
- **Оригиналы.** Синхронизируются оригиналы (включая Live Photo и RAW-пары), а не обработанные версии.
- **Один Mac на облако.** Одновременная работа нескольких Mac с одним облачным каталогом не поддерживается.
- **Два языка.** Интерфейс на русском и английском.

## Требования (план)

- macOS 13–27 (схему «Фото» каждой следующей версии macOS добавляют после проверки), Apple Silicon и Intel, один универсальный бинарник (запуск на macOS 13 ещё не проверен).
- Системная медиатека «Фото» и разрешения macOS: доступ к «Фото» и, возможно, полный доступ к диску (для чтения базы «Фото»). Из терминала право на «Фото» фактически общее для всего, что запускается из этого терминала; процесс, запущенный через LaunchAgent, получает собственное право.
- Для конвертации неподдерживаемых видеоформатов в MP4 — установленный `ffmpeg` (только если эта политика включена).

## Установка

Релизов пока нет. Так будет выглядеть установка.

1. Скачать архив и `checksums.txt` со страницы Releases: `gh release download <тег> -R Windemiatrix/photosync -p 'photosync_*_darwin_universal.tar.gz' -p checksums.txt` (или `curl -LO`). До `v1.0.0` берите конкретный тег со страницы Releases, а не `latest`.
2. Проверить хеш: `grep darwin_universal checksums.txt | shasum -a 256 -c -`.
3. Проверить происхождение: `gh attestation verify photosync_<версия>_darwin_universal.tar.gz --repo Windemiatrix/photosync` (точные флаги, в том числе `--signer-workflow` с workflow релиза, уточняются).
4. Распаковать и положить в `PATH`: `tar xzf ... && install -m 755 photosync ~/bin/`.
5. Если файл скачан браузером и macOS блокирует запуск: `xattr -d com.apple.quarantine ~/bin/photosync` (только для этого файла и только после проверки).

Контрольная сумма защищает только от порчи при скачивании: она лежит рядом с архивом. Подлинность (собрано из этого репозитория workflow релиза) подтверждает только `gh attestation verify`; без `gh` подлинность проверить нельзя.

Бинарник подписан только ad-hoc подписью: он не подписан Apple и не нотаризован, поэтому macOS может его блокировать, а процесс, запущенный через LaunchAgent, после обновления может заново запросить доступ к «Фото» (при запуске из терминала право сохраняется). `photosync doctor` и заметки к релизу предупреждают об этом.

Через `go install` ставить не рекомендуется: такой бинарник подписан линкером Go с именем `a.out`, и macOS показывает в запросе доступа и в настройках «a.out». Бинарник из релиза подписан с идентификатором `io.github.windemiatrix.photosync`. Реквизиты OAuth-приложения photosync встроены только в релизные сборки: сборка без них (`go install`, локальная) войти в Яндекс не может и сообщает об этом.

**Обновление** ручное, теми же путями: самообновления и проверки версии по сети нет. Бинарник старее базы состояния откажется работать; откат бинарника возможен, пока миграция не применялась, или из резервной копии базы.

**Удаление.** Сначала для каждого хранилища выполните `photosync remote logout <имя>`: команда удаляет файл токенов `~/.config/photosync/tokens/<имя>.json` и отзывает доступ у Яндекса. Затем по отдельности убираются:

- бинарник;
- каталог состояния `state_dir` (по умолчанию `~/Library/Application Support/photosync`) и конфигурация `~/.config/photosync/`;
- в облаке: каталог `.photosync/` (карантин и `owner.json`), если облако больше не синхронизируется. Пока `owner.json` на месте, другая установка photosync (с другим `state_dir`) не сможет работать с этим облаком.
