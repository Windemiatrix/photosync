Сжатый обзор устройства приложения. Кода пока нет: документ описывает проектируемое поведение. Места, зависящие от ещё не проверенных фактов о macOS, PhotoKit и iCloud, помечены как неподтверждённые. Идентификаторы `R-*` (правила плана) и `INV-*` (инварианты) и ключи конфигурации (`targets.*`, `remote_priority`, `sync.*`, политики `conflict`, `deletes` и другие) названы здесь заранее: их полный перечень появится вместе с кодом и справочником по настройке.

## Термины

- **Хранилище** — облако, с которым работает программа. В первой версии это Яндекс Диск через его REST API; контракт хранилища нейтральный и от протокола не зависит. «Облако» в тексте означает то же самое.
- **Объект** — запись «Фото»: фотография, видео, Live Photo или RAW-пара.
- **Снимок** — состояние медиатеки «Фото» (объекты и альбомы), прочитанное в память на время запуска.
- **Связь** — запись о том, что объект соответствует файлу в хранилище (путь, размер, хеши).
- **Событие** — альбом «Фото» вида `ММ/ДД Название` внутри папки года; ему соответствует каталог `ММ-ДД - Название`. **Тематический альбом** — любой другой альбом.
- **Карантин** — каталог `.photosync/quarantine` в облаке: вместо удаления файл переносится туда.

## 1. Две поставки

Библиотека [osxphotos](https://github.com/Windemiatrix/go-libs/tree/main/osxphotos) не знает о синхронизации: читает копию `Photos.sqlite`, строит пути по шаблонам, даёт мост к PhotoKit. Ввод-вывод библиотеки (`photosdb`, `photokit`) приложение подключает через один адаптер, чистые пакеты `template` и `export` домен импортирует напрямую (§2). Приложение зависит от опубликованных тегов библиотеки, `replace` в `go.mod` запрещён. Принцип: из двух решений берётся более простое, пока не доказано, что оно не справляется.

## 2. Компоненты

```text
cmd ──► app ──► domain
cmd ──► adapters ──► domain      (app адаптеры не импортирует; адаптеры не импортируют app)
cmd, app ──► state, report, clock
cmd ──► config, i18n             (state, report, clock, config, i18n — конкретные пакеты, без интерфейсов)
```

Структура кода следует образцу [bxcodec/go-clean-arch](https://github.com/bxcodec/go-clean-arch): `app` — слой сервиса, `adapters` — repository, `cmd` — delivery; интерфейсы объявляет тот, кто их использует, отдельного пакета интерфейсов нет, зависимости направлены внутрь, к `domain`.

- **`domain`** — чистые правила без ввода-вывода (из внешних пакетов — только `x/text` и чистые пакеты `template` и `export` библиотеки osxphotos): имена файлов, даты, раскладка по папкам и альбомам, сопоставление, план. План — чистая функция, поэтому проверяется табличными тестами по правилам `R-*` и property-тестами.
- **`app`** — сценарии (`init`, `doctor`, `plan`, `sync`, `conflicts`, `albums diff`, `undo`, `explain`, `relink`, `import-state`, ...): управляют вводом-выводом через свои интерфейсы, пулы обработчиков.
- **`adapters`** — реализации интерфейсов, которые объявляет `app`; решений не принимают.
- **Конкретные пакеты** (без интерфейсов: тесты берут их настоящими, в том числе SQLite; у `clock` есть управляемая тестовая реализация): `state` (SQLite), `report` (`json/md/csv`), `clock`, `config`, `i18n` (ru/en).

Интерфейсы `app`: `PhotoLibrary` (снимок через `photosdb`; скачивание, импорт, альбомы, удаление через `photokit`); `Remote` (нейтральный контракт хранилища; адаптер первой версии — REST API Яндекс Диска; облако сканируется рекурсивным параллельным обходом папок, плоского списка нет); `MediaProbe` (свой разбор EXIF/ISOBMFF/QuickTime по Range-запросам); `Converter` (`ffmpeg`); `SpaceManager`, `NetworkMonitor`; `UI` (без полноэкранного интерфейса). Границы слоёв проверяет линтер. У каждого cgo-адаптера есть заглушка для других ОС; CI собирает и тестирует только на macOS.

Основные команды:

| Команда | Что делает |
|---|---|
| `init` | мастер настройки: хранилища, вход в Яндекс по коду, политики |
| `remote auth`, `remote logout` | вход по коду для https://ya.ru/device; выход удаляет файл токенов и отзывает доступ |
| `doctor` | проверка окружения, прав и доступности хранилищ |
| `status` | показывает текущее состояние синхронизации |
| `plan` | строит и показывает план, ничего не меняя в данных |
| `sync` | строит план и, с `--apply`, выполняет его |
| `conflicts` | список открытых конфликтов; `conflicts resolve` записывает решение |
| `albums diff` | расхождения между альбомами «Фото» и каталогами облака |
| `undo` | откат последнего применённого запуска (с `--apply`) |
| `explain` | показывает, по какому правилу `R-*` принято решение |
| `relink` | вручную исправляет связь объекта с файлом |
| `import-state` | загружает связи из материалов прежней ручной синхронизации; с `--apply` записывает их в состояние, и план после этого не содержит передач для уже связанных файлов |

Служебные команды (проверка конфигурации, просмотр хранилищ и журнала, версия) здесь не перечислены: их список появится вместе со справочником.

## 3. Данные и состояние

`state_dir` содержит `state.db` (SQLite), `lock`, `tmp/` и отчёты `runs/<run_id>/` (план, журнал, итог; 90 дней). Миграции только вперёд; перед ними делается копия `state.db.bak-<версия>`, база новее бинарника вызывает отказ. Конфигурация: `~/.config/photosync/config.yaml`; токены доступа: `~/.config/photosync/tokens/<remote>.json` (файл `0600` в каталоге `0700`).

- `assets`, `asset_resources`, `asset_history` — копия снимка последнего применённого запуска и прежние идентификаторы после замен.
- `albums`, `asset_albums`, `album_map` — альбомы, папки, членство и пары «альбом или папка ↔ каталог», которые не пересчитываются.
- **`links` — база трёхстороннего сравнения:** для пары «объект, хранилище» путь, размер, хеши, `etag`, роль, уровень сопоставления, статус (`active`, `quarantined_*`, `detached`).
- `conflicts`, `runs`, `journal` (с прежними значениями для отката), `probe_cache`.

Таблицы состояния, кроме `runs` и `probe_cache`, меняют только пять команд: `sync --apply`, `undo --apply`, `import-state --apply`, `relink` и `conflicts resolve`; `plan`, `status`, `explain`, `doctor`, `albums diff` пишут только строку `runs`, файлы отчёта и кеш метаданных облака `probe_cache`. Скан облака в состоянии не хранится: он живёт в памяти запуска. Выведенное из снимка пишется в фазе 0 `sync --apply` одной транзакцией (фазы описаны в §4). Объект опознаётся по облачному GUID (есть у всех объектов и уникален; его неизменность после пересоздания объекта ещё предстоит проверить с iCloud), затем по UUID, затем по истории замен; альбом — по облачному GUID (есть и уникален), иначе по `PHCloudIdentifier` или пути с названием.

## 4. Как работает синхронизация

Раскладка в облаке: `Год/ММ-ДД - Название` для событий, `Год/ММ-ДД` для объектов без события. Формат имени события фиксирован; событию без названия подставляется текст из ключа `sync.untitled_event` (его записывает `init`). Остальные (тематические) альбомы синхронизируются там, где у объекта есть связь в каталоге такого альбома. Многозначные поля шаблона дают одно значение (основное размещение). Смена `path_template` действует только на новые файлы. Общая и личная медиатеки iCloud раскладываются в разные корни хранилища (`targets.shared` и `targets.personal`). Импорт сразу в общую медиатеку ещё не подтверждён (нужна проверка с iCloud): если он не получится, объект попадёт в личную и будет ждать ручного переноса по отчёту.

Один запуск `plan` или `sync` — семь шагов:

1. **Снимок «Фото»** в памяти. Общие альбомы (не путать с общей медиатекой) и несохранённые объекты из «Общее с вами» отбрасываются, скрытые и невыбранные кадры серий подчиняются политикам; невыбранные кадры идут в папку события ключевого кадра. Получение скрытых объектов и невыбранных кадров через PhotoKit ещё не подтверждено.
2. **Скан облака** по всем хранилищам: при каждом запуске настроенные папки обходятся рекурсивно и параллельно. Любая ошибка обхода фатальна: частичный скан не трактуется как «файлы удалены». Файлы моложе `sync.settle_minutes` минут не трогаются. Каталоги из `sync.edited_dirs` и файлы `*_edited.*` считаются правками и подчиняются политике `edited_files`.
3. **Обогащение:** даты файлов без связи читаются Range-запросами; если хранилище не даёт хеш, файл скачивается и хешируется.
4. **Сопоставление новых.** Уровни от надёжного к слабому: `exact`, `same_shot`, `same_shot_weak`, `same_time_size`, `probable`, `pair_component` (компонент Live или RAW-пары). Назначение один-к-одному, жадное, с полным порядком кандидатов; одно имя связи не создаёт. Пара с разным содержимым (пережатая копия, экспорт в другой формат) — `derived_copy`: лучшим считается файл с большим числом пикселей, затем RAW, затем с большим размером в байтах.
5. **Трёхстороннее сравнение** базы, «Фото» и облака. Одинаковые изменения с двух сторон не конфликт, «изменён против удалён» решается в пользу изменения. Изменения всех хранилищ сводятся в целевое состояние «Фото» (при расхождении хранилищ побеждает более приоритетное по `remote_priority`), затем строятся операции по каждому хранилищу. Конфликты решает политика `conflict` (рекомендуется `remote_wins`; `ask` и `skip` исключают объект и дают код 2). Правила имеют идентификаторы `R-*` для `explain`.
6. **Отчёт:** сводка, файлы плана, `plan_digest` в `runs`. Снимок и связи не меняются.
7. **Применение** (только `--apply`): план строится заново и сверяется по `plan_digest` с просмотренным. Выполняется в фазах 0–6.

Фазы применения: **0** запись снимка и связей, `owner.json` в облаке; **1** каталоги, перемещения, копии, карантин, удаление файлов и пустых каталогов в облаке (при `deletes: propagate`; файлы уходят в корзину Яндекс Диска), папки и альбомы в «Фото»; **2** «Фото» → облако (оригинал на диск, хеш, атомарная загрузка в каждое хранилище; передачи идут параллельно, число параллельных передач в обе стороны задаёт `limits.parallel` (по умолчанию 256; для медленного канала его стоит уменьшить; скан облака им не ограничен)); **3** облако → «Фото» (скачивание, разбор, при необходимости конвертация, импорт с альбомами; MP4, полученный политикой `convert_mp4` — конвертацией неподдерживаемых видеоформатов через `ffmpeg`, — уходит и в остальные хранилища); **4** членство в альбомах, обновление объектов; **5** удаление объектов «Фото» одним пакетом через системное окно macOS, замены; **6** уборка.

**Первая синхронизация** заполненных библиотек: пары альбомов подбираются по имени, затем по составу, остальные создаются; расхождения членства решает политика `conflict`, итог виден в `photosync albums diff` до применения. Файлы, уже лежащие в облаке, связываются с объектами и повторно не загружаются.

Повторы: до 6 попыток с экспоненциальной задержкой; после трёх подряд безуспешных операций хранилище в этом запуске пропускается. Коды возврата: 0 успех, 1 ошибка или отказ, 2 открытые конфликты, 3 нет места, 130 Ctrl+C.

## 5. Защита от потери данных

- **`--yes` не принимается** (без терминала — код 1 с указанием, что нужно: флаг или запуск в терминале), если:
  - просмотренного плана нет или он изменился: нужно ручное подтверждение в терминале;
  - есть необратимые операции (удаление в облаке при `deletes: propagate`): нужно ввести их число в терминале;
  - удалений, карантинов и замен больше порога (50 объектов или 5 %): нужен `--allow-mass-changes` или ввод числа;
  - на первой синхронизации вероятных пар (`same_time_size`, `probable`) больше 1 %: нужны просмотр выборки и отдельное подтверждение или `--confirm-probable`.
- **Удаления.** Политика `deletes` обязательна, значения по умолчанию нет: `none` (не переносить), `quarantine` (рекомендуется) или `propagate`. Карантин в облаке: `.photosync/quarantine/<дата>`, по умолчанию 90 дней (`sync.quarantine_keep_days`). При `propagate` удаление в облаке необратимо для photosync: файл уходит в корзину Яндекс Диска, `undo` его оттуда не возвращает, вручную он восстановим до очистки корзины и до тех пор занимает квоту. Истёкший карантин и `.photosync/tmp` удаляются безвозвратно, минуя корзину. Удаление в «Фото» идёт в «Недавно удалённые» и подтверждается системным окном.
- **Облако.** Перемещение и копирование никогда не перезаписывают занятое назначение, кроме перемещения в карантин внутри `.photosync/`. Условных операций в REST нет, поэтому перед удалением, карантином и заменой `Stat` сверяет размер и `etag` с записью связи в `links`. Каталоги вне `.photosync/` рекурсивно не удаляются, корень хранилища неприкосновенен. Пути из облака недоверенные: `path.Clean`, проверка префикса, NFC. Загрузка атомарна: запись в `.photosync/tmp`, затем перемещение без перезаписи.
- **Откат.** `undo --apply` откатывает только последний применённый запуск, строго по порядку, по журналу с прежними значениями; изменившаяся после запуска цель пропускается и попадает в отчёт. Неоткатываемое видно заранее.
- **Возобновление.** Операции идемпотентны, связь пишется сразу после каждой передачи, импорт перед повтором ищется по признакам из журнала. Сбой на любой границе не даёт двойного импорта.
- **Один запуск и один Mac.** Изменяющие команды берут блокировку `state_dir/lock`; `<корень>/.photosync/owner.json` закрепляет облако за одним состоянием, чужое получает отказ. Несколько Mac на одно облако не поддерживаются. Применение отказывается, если медиатека не системная или не та, что записана.
- **Секреты, сеть, входные данные.** Паролей нет: вход по коду устройства. OAuth-токены лежат в файле `~/.config/photosync/tokens/<remote>.json` (`0600` в каталоге `0700`, запись атомарна; файл с правами шире `0600`, каталог шире `0700`, символическая ссылка или чужой владелец — отказ, `doctor` называет команду исправления), не в Связке ключей, и не попадают в аргументы, вывод и журналы. Реквизиты OAuth-приложения встроены в релизные сборки и публичны (извлекаются из бинарника); секрет — только токены пользователя. Сборка без них (`go install`, локальная) войти в Яндекс не может и сообщает об этом. Только `https://` (`http://` допускается лишь для loopback-адресов в тестах; проверку сертификатов отключить нельзя). Сетевые обращения идут только к API Яндекс Диска, его хостам передачи файлов (токен на них не отправляется) и OAuth Яндекса. Размеры ответов ограничены, `ffmpeg` запускается с белым списком демультиплексоров, имена из облака экранируются в терминале и CSV.

## 6. Тестирование

- **Домен:** таблицы по правилам `R-*`; property-тесты инвариантов `INV-*` (после применения план пуст, порядок детерминирован, последний оригинал не исчезает, операции не выходят за корень, нет двойного импорта).
- **Сопоставление:** генератор миров с известной истиной; фикстуры из обезличенных материалов с результатом, проверенным человеком; перед коммитом они проходят сканер утечек и ручной просмотр выборки мейнтейнером.
- **Сценарии `app`:** настоящий пакет `state` (SQLite); адаптер Яндекс Диска против эмулятора REST API с отказами (429, 503, обрыв, потерянный ответ); фейки «Фото», места, сети. Сбой на любой границе операции даёт тот же итог, что запуск без сбоя.
- **Контракты:** один набор проверок для всех реализаций `Remote` (эмулятор REST API; интеграционные тесты на отдельном тестовом аккаунте Яндекса в GitHub Actions) и `PhotoLibrary`.
- **Прочее:** фаззинг парсеров; равенство ключей ru и en; с `--output json` в stdout ровно один валидный JSON-документ.
- **PhotoKit:** тесты с тегом `photokit_live` (импорт, удаление, альбомы на настоящей медиатеке) запускаются только вручную под отдельной учётной записью macOS с отдельным Apple ID и тестовой медиатекой, никогда на основной медиатеке. В CI на одноразовом раннере с его собственной медиатекой проходит только smoke-прогон импорта, выгрузки и альбомов; удаление требует системного диалога и в CI не проверяется.

Покрытие: не ниже 80 % в сумме по всем пакетам (`make cover`); порог 95 % для каждого пакета домена появится вместе с первым из них.

## 7. Сборка

Бинарник с cgo (PhotoKit, мониторинг сети, свободное место) собирается только на macOS: `MACOSX_DEPLOYMENT_TARGET=13.0`, `-trimpath`. Срезы arm64 и amd64 объединяются `lipo` в universal, затем ставится обязательная ad-hoc подпись `codesign -s - --identifier io.github.windemiatrix.photosync` (без идентификатора macOS видит бинарник как `a.out`; не подпись Apple и без нотаризации, сертификаты не нужны); архив и суммы считаются после неё. `Info.plist` с описанием доступа к «Фото» встраивается директивой в `cmd/photosync`. Сборку описывает один конфиг: локально — `make release-snapshot` (входит в `make test`), в job релиза после слияния — `goreleaser release` с шапкой заметок `docs/release-notes-header.md`; побитовая воспроизводимость не обещается, происхождение подтверждает аттестация.

**Не проверено:** совместимость ad-hoc подписи с hardened runtime (он пока выключен); запуск на macOS 13 (проверяется чеклистом релиза).

## 8. Выпуск

**Ветки и PR.** Работа ведётся в ветках `<тип>/<тема>`; каждое изменение приходит в `main` через PR без обязательных одобрений: владелец сливает его squash после зелёного CI. Заголовок PR становится заголовком коммита в `main` (Conventional Commits, на английском, до 70 символов; GitHub дописывает номер PR). Force-push и удаление `main` запрещены, теги неизменяемы; внешние участники идут тем же путём.

Версии: semver без предрелизов, версию вычисляет svu из заголовков PR (`!` после scope — несовместимое изменение, `feat` — minor, остальное — patch; до `v1.0.0` несовместимое изменение даёт minor); `v1.0.0` ставится явно, ручным запуском. `go.mod` релиза ссылается на опубликованный тег библиотеки, без псевдоверсии и без `replace`. Релиз выходит после каждого слияния PR в `main`: когда CI зелёный, job `release` вычисляет версию, собирает релиз и публикует GitHub Release с тегом на этом коммите.

Состав: `photosync_<версия>_darwin_universal.tar.gz` (бинарник, `LICENSE`, README), `checksums.txt`, аттестация происхождения. Отдельных архивов по архитектурам, SBOM и Homebrew в первой версии нет. Заметки содержат инструкцию проверки на двух языках и список изменений на английском из заголовков PR (squash-коммитов между тегами). Ручной чеклист на чистой учётной записи (arm64 на Apple Silicon, amd64 на Intel или через Rosetta; macOS 13 и новейшая) выполняется на опубликованном релизе; найденную ошибку закрывает следующий релиз.

## 9. Установка и обновление

Пошаговая инструкция (скачивание, проверка, установка, обновление, удаление) лежит в [README](../README.md#установка), права macOS описаны там же в разделе «Требования (план)». Здесь — дополнения к README: право «Фото» процесса LaunchAgent привязано к бинарнику (ad-hoc подпись — к хешу кода), поэтому после обновления macOS может запросить его заново; при запуске из терминала действует право терминала; `go install` даёт бинарник с подписью линкера `a.out` и не рекомендуется.
